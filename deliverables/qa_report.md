# Data Quality Report

Source of truth: `pre and post final.xlsx`, recomputed directly from the raw data.
Generated by `analysis/analysis.py`; all figures below are read from `analysis/results.json`.

## 1. Structural checks

- Pre sheet: 75 rows, 14 columns. No duplicate `session_id` values (0 duplicates).
- Post sheet: 37 rows, 16 columns. No duplicate `session_id` values (0 duplicates).
- No missing values in any closed-choice (single/multi-select, slider) column used for KPI calculations, in
  either sheet. Missingness is confined to two optional open-text fields:
  - pre `open_giveup_story`: 52 of 75 rows blank (18 of 61 *eligible* respondents answered).
  - post `open_confusion`: 29 of 37 rows blank (8 answered; 4 of those were substantive after cleaning trivial
    "no"/"nothing" answers).

## 2. Screener application

The screener was re-derived independently from the raw answers to `age_band`, `stream_freq`,
`eat_while_watch`, and `meal_sessions_per_week`, following the rules on the screener spec board and in
`Pre-Post Survey — Problem Validation.docx` (S1–S3, Q1):

- Age is "Under 18" or "31 or older" → screen out (7 respondents)
- Streaming frequency is "Rarely" (or "Never", not present in this data) → screen out (8 respondents)
- Never watches while eating a meal → screen out (1 respondent)
- 0 meal-watch sessions per week → screen out (4 respondents)

A respondent can fail more than one rule, so the four counts above do not sum to the total screened out.
This independent recomputation **exactly reproduces** the sheet's own `screened_out` flag for all 75 rows
(75/75 match) — the flag in the source file is trustworthy and was used directly downstream, with the
recomputation kept as the audit trail.

**Result: 75 submitted → 61 eligible (14 screened out) → 37 completed the post survey.**

Eligible respondents are the only valid denominator for any pre-survey (C1–C5) statistic. No screened-out
respondent's answers appear in any KPI in this analysis.

## 3. Pre/post matching

- Joined on `session_id` (inner join, eligible pre ∩ post).
- All 37 post `session_id` values are found in the pre sheet (0 orphaned post rows).
- All 37 post respondents map to an *eligible* pre respondent — 0 post rows trace back to a screened-out pre
  respondent (which would have been invalid and excluded).
- 24 of the 61 eligible pre respondents did not complete the post survey (attrition).
- **Completion rate = 37 / 61 = 60.7%.**

## 4. Screener/question-set cross-check against the survey spec

Cross-referencing `Pre-Post Survey — Problem Validation.docx` against the actual columns in the Excel export
surfaced a few option-set differences, documented in full in `results.json → spec_crosscheck`:

- Two pre-survey options defined in the spec (`Q4`: "Almost every time"; `Q6`: "Gave up and just ate") never
  appear in the export — they received zero responses, they are not missing data.
- One post-survey option (`Q6`: "None") likewise never appears — every respondent who answered found at least
  one component useful.
- The post sheet contains one extra item (`taste_match`) not in the spec's Q1–Q9 list; it is reported
  separately and not folded into any spec-defined KPI.
- The spec's own measurement-plan section has an internal inconsistency in how it numbers the likelihood-to-use
  question; columns were therefore matched to spec questions by header text, not by assumed position/number.

## 5. Behavioural vs. survey measures

Every C1–C5 problem-validation figure is **self-reported/recalled**, not logged behaviour. Every solution
validation figure is a **stated reaction** to a single short prototype exposure, not observed repeat use. No
event log (impressions, clicks, dwell, play-starts) exists in this dataset — see Dashboard Section 9 for the
full list of behavioural KPIs this would unlock and the fields required.

## 6. Verdict

The dataset is internally consistent (screener flag reproduces exactly, all joins are clean, no missing data
in any closed-choice field) and is fit for the survey-based analysis in this report. It is **not** sufficient,
on its own, to certify the feature for launch — that requires the instrumented behavioural test described in
Dashboard Section 11 ("Test Next").
